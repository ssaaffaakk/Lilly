# Translation quality — what Lilly actually serves (English → Bosnian)

Scored build: `6f240bb14aa56ea7ae1c8a19cb25faab`

2,009 FLORES-200 pairs the base model was not trained on. Both models are int8 CTranslate2 builds and both go through `app.translate.Engine`, so the sentence splitting and the quantisation are the product's own. The only difference between the two columns is the fine-tuning.

This is the number to quote. `training/RESULTS-en-bs.md` scores the PyTorch base plus its LoRA adapter and feeds each row in whole — the path the published 29.57 → 30.73 BLEU came from. Neither the quantisation nor the sentence splitting is in that number, and both are in what a reader meets, so the two are not interchangeable.

The base model prints its language tag into the translation itself — `>>bos_Latn<<` and friends — in 0 of 2,009 outputs (0.0%). Lilly does it in 0 (0.0%). That is a defect in what the model emits, so the scores are given both with it and without: with, because it is what the model learned to write; without, because otherwise the fine-tuning gets credit for translation quality it did not gain. The app strips a leaked tag before answering (since 8 September 2026), so a reader sees the second table.

## Intervals, the devtest half, and what this number does not settle

Added by hand beside the generated tables above, because a delta without an
interval is not a reported number. Both come from
`training/verify_published_en_bs.py`, a paired bootstrap over sentences, 1,000
resamples, seed 11, on the same stored outputs the tables were scored from.

| Gap, 2,009 pairs | Point | 95% interval | Resamples at or below zero |
|---|---|---|---|
| BLEU | +0.99 | [+0.47, +1.46] | 0 of 1,000 |
| chrF2 | +0.62 | [+0.33, +0.89] | 0 of 1,000 |

The devtest half alone — 1,012 segments, the set published leaderboards for this
pair use, so the only column that may be put beside somebody else's system:

| Model | BLEU | chrF2 |
|---|---|---|
| Base (untuned) | 31.49 | 61.03 |
| Lilly (fine-tuned) | 32.45 | 61.75 |
| **Gap** | **+0.96** (p = 0.003) | **+0.72** (p = 0.001) |

**Against the published adapter-path numbers.** `training/RESULTS-en-bs.md`
reports 29.57 / 58.96 → 30.73 / 60.00 on these same 2,009 pairs. Those four
figures reproduce exactly from `training/hypotheses-en-bs.json`, so nothing
there is wrong; they simply describe a different path. Read side by side:

| | Published path (PyTorch + LoRA, whole rows) | Served path (int8, app splitter) |
|---|---|---|
| Base | 29.57 / 58.96 | 31.23 / 60.93 |
| Lilly | 30.73 / 60.00 | **32.22 / 61.55** |
| Gap | +1.16 / +1.04 | +0.99 / +0.62 |

The served build is **+1.49 BLEU and +1.55 chrF2 above the published figure**,
and the fine-tuning's own share of it is **smaller** than published (+0.99
against +1.16 BLEU, +0.62 against +1.04 chrF2). Both moves come from the same
cause: the sentence splitter lifts both columns, and it lifts the untuned base
more than it lifts the fine-tune, because part of what the fine-tune learned was
to survive multi-sentence rows the app never hands it. The forward direction
showed the same shape (+0.54 BLEU raw against +1.23 through the app, see this
file's bs-en twin `training/RESULTS-product.md`).

**What this does not settle.** `training/RESULTS-bosnian-audit.md` measures
FLORES's Bosnian side at 49% Bosnian by lexical marker against this project's
training data at 77%. In this direction the Bosnian text is the *reference*, so
part of any chrF2 movement here is a measurement of which standard the reference
was written in rather than of translation quality. The form-rate instrument
(`training/RESULTS-en-bs-formrate.md`, 94.3% → 99.2% on 338 audited targets) is
the one that tests the Bosnian-versus-Croatian question head-on, and it is not
affected by this, because it asks which form the model *wrote*, not how closely
it matched a reference of uncertain standard.

The served-path translations are not committed: `training/app-hypotheses*.json`
is untracked here exactly as it is for the forward direction. The build
fingerprint above is what binds this number to those weights. Re-running costs
about four hours of laptop CPU for both columns.
